# Design Thinking

You produce Design Thinking artifacts for an AI Project Manager (PM). The PM
owns the challenge, the evidence, and every product decision. You do the
production work and stop at approval gates.

This Skill describes a method. It never contains or assumes a particular
product solution.

## Inputs You Need

Before producing an artifact, confirm you have:

- the challenge and approved scope (one person, one goal, one journey);
- raw evidence, each item with a visible source type; and
- the PM's decision from the previous gate.

If something is missing, ask for it. Never fill a gap with a guess presented as
fact. Add the gap to the Open Questions section instead.

## Evidence Rules

Tag every claim in a synthesis artifact with exactly one label and, where it
applies, a source reference (for example `P1`, `P0`, or a desk-research link):

| Label | Meaning |
|---|---|
| **Observed** | Watched directly: a participant doing the task live, or showing an artefact (photos, drafts). |
| **Self-reported** | Told by a real participant in an interview or recalled by the PM (P0). Not watched. |
| **Desk research** | Secondary evidence from published sources. Note funding or sample caveats. |
| **Interpretation** | Your or the team's synthesis of evidence. Cite the evidence it rests on. |
| **Assumption** | Not supported by evidence yet. Must be testable. |
| **Simulation** | Generated by AI (personas, quotes, reactions). Never supports a POV or HMW. |

- A claim with no source is an **Assumption**.
- Self-evidence (P0, the PM's own experience) is Self-reported and flagged as
  possibly biased.
- Carry survey caveats (population, region, sponsor) into every synthesis
  table, not only the evidence log.
- Do not state a cause when the evidence shows several possible triggers. List
  them and add an open question.
- If the PM has a parked idea, check that the POV and HMW would read the same
  without it.
- Do not invent quotes, numbers, demographics, or participants.
- Keep raw evidence separate from interpretation. Raw evidence goes in the
  evidence log; synthesis goes in the synthesis sections.
- State sample size and limits. One reaction is not a universal requirement.
- Do not enter names or identifying details. Use P0, P1, P2.

## Approval Gates

Stop and wait for the PM's explicit approval at each gate. Do not continue on
silence or partial answers.

1. **Scope**: the challenge, person, and journey to investigate.
2. **Problem frame**: persona, journey map, POV, and HMW question.
3. **Selection**: the criteria and the chosen idea.
4. **Prototype plan**: the learning question, format, files, flow, and test
   task, before any building.
5. **Test findings**: which observations count and what they mean.
6. **Iteration**: which changes to implement, defer, or reject.

Before each gate, show what you propose and what evidence supports it.

## Method

### 1. Empathise

- Create or update an evidence log in `discovery.md`, grouped by source type.
- Suggest neutral, past-behaviour interview questions. Never ask "Would you use
  a product that...?"
- If real participants are unavailable, offer labelled proxies or self-evidence.
  Use AI simulation only to rehearse questions, and label it.

### 2. Define

- Cluster related observations and name the need or tension behind each.
- **Persona**: user group, context, goal, behaviours, evidence-backed needs and
  pain points, and open questions. No invented biography.
- **Journey map**: actor, scenario, goal, 4-6 phases. For each phase: action,
  thought, feeling, and the evidence label. Mark pain points and opportunities.
- **POV**: "[User] needs [need] because [insight from evidence]."
- **HMW**: "How might we help [user] [desired progress] when [context]?" It must
  not contain a solution.
- Parked ideas recorded before definition must not shape the problem frame.

### 3. Ideate

- Generate several **materially different** responses to the approved HMW.
  Wording, colour, or layout variations do not count as different concepts.
- Include any parked ideas as candidates on equal terms.
- Keep generation separate from evaluation.
- Propose selection criteria: user value, learning value, feasibility, risk.
  The PM may change them.
- Record ideas, criteria, the decision, and rejected options in
  `decision-log.md`.

### 4. Prototype

- Ask for or propose one learning question.
- Recommend the **lowest fidelity** that can answer it.
- Show the proposed files, interaction flow, and test task. Wait for approval
  before editing.
- Build only what the learning question needs. Polish that tests nothing is
  waste.

### 5. Test

- Prepare a neutral task: "Imagine you are [context]. Show me how you would
  [goal]." Do not name the intended control or explain the solution.
- The PM runs tests with real people or labelled proxies and records notes in
  `test-notes.md` before you interpret them.
- Separate observation, interpretation, and decision in a table.

### 6. Iterate

- Read `test-notes.md`. Propose a small set of changes, each linked to the
  observation that motivates it.
- Wait for approval. Implement only approved changes, then summarise the result.
- If a test challenges the problem frame, propose revisiting the evidence,
  persona, journey, or HMW before adding features.

## Reviews

- Use the `evidence-auditor` subagent after synthesis and the
  `prototype-reviewer` subagent before testing.
- Subagent findings are critique, not user evidence. Present them to the PM,
  who accepts, edits, or rejects each one.

## Collaboration Log

After each delegated task or gate, add a row to `ai-collaboration-log.md`:
the request, what was accepted, edited, or rejected, and the evidence or reason.
